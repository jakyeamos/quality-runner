# Maintenance-Surface Evidence

`qr maintenance-surface` describes the maintenance surface introduced or removed
by a Git comparison. It reports evidence for review; it does not score design
quality, impose a line-count budget, mutate the target repository, or authorize
implementation.

## What it records

- exact requested and resolved base/head provenance;
- changed files and production, test, and other line deltas;
- newly declared dependencies in common manifests;
- candidate public surfaces, flags/configuration, and compatibility seams;
- author-declared supported behavior and concepts consolidated;
- residual-reference observations for removed declarations or files;
- opt-in behavior-owner and compatibility contracts; and
- optional proof that a named regression test failed on a defective revision and
  passed on the fixed revision.

Candidate detection is intentionally conservative and review-required. A match
is not proof of a new API, incomplete deletion, or unjustified compatibility
layer. Counts describe the selected diff and are never a pass/fail threshold.

Normal `qr inspect`, `qr run`, and `qr refresh` scans also project added
dependencies, public/configuration/compatibility candidates, invalid contracts,
and residual-removal observations into `code-quality-scan.json` as native
`maintenance-surface` findings. The full evidence remains available through
`qr maintenance-surface`; scan findings are review signals, not authorization to
remove a dependency or surface.

To keep the normal finding queue actionable, candidate projections are limited
to paths admitted by the code-quality scan, exclude test-only paths, and collapse
repeated matches into one finding per file and signal type. The standalone
artifact retains the complete candidate inventory and raw counts.

Repository scans compare `HEAD` with the current worktree. A refresh using
`--diff-base` reuses that branch-diff base and includes the worktree only when
the resolved scan scope includes it.

Repositories that must suppress this scan projection can explicitly add
`"maintenance-surface"` to
`quality_runner.structural_scan.disabled_rule_groups`; the standalone evidence
command remains available.

## CLI

Compare the current worktree with `HEAD`:

```sh
qr maintenance-surface . --json
```

Compare a branch with its merge base against `origin/main` and write review
artifacts:

```sh
qr maintenance-surface . \
  --base origin/main \
  --head HEAD \
  --behavior-added "repository owners are visible in review" \
  --behavior-removed "parallel compatibility owner" \
  --consolidated-concept "repository status owner" \
  --regression-proof regression-proof.json \
  --output maintenance-surface.json \
  --handoff-output maintenance-surface.md \
  --json
```

`WORKTREE` is the default head. For two revisions, Quality Runner uses their
merge base as the comparison base and records all three resolved commits.

## Optional repository contracts

Contracts are disabled unless explicitly enabled in `.quality-runner.toml`.
Path patterns use repository-relative glob matching.

```toml
[quality_runner.maintenance_surface]
enabled = true

[[quality_runner.maintenance_surface.behavior_owners]]
id = "repository-status"
owner = "src/repository/status.ts"
paths = ["src/repository/**"]
description = "One owner for repository state and its public projection."

[[quality_runner.maintenance_surface.compatibility]]
id = "legacy-status-shape"
consumer = "desktop clients before 3.2"
owner = "src/repository/status-compat.ts"
behavior = "Preserve the legacy serialized field names."
removal_condition = "Remove after desktop 3.1 is outside the supported window."
paths = ["src/repository/status-compat.ts"]
```

When enabled, each detected public-surface or compatibility candidate must map
to exactly one relevant declaration. Invalid or duplicate declarations block
the evidence artifact; unmatched candidates stay review observations.

## Regression proof

Verified evidence is explicit and never generated by checking out or executing
an old revision automatically:

```json
{
  "schema": "quality-runner-regression-proof-v0.1",
  "status": "verified",
  "test": "pytest tests/test_status.py::test_legacy_status_shape",
  "defective_revision": "abc1234",
  "defective_result": "failed",
  "fixed_revision": "def5678",
  "fixed_result": "passed",
  "evidence": ["CI run 1042", "CI run 1047"]
}
```

If the historical run is unsafe or unavailable, record that boundary:

```json
{
  "schema": "quality-runner-regression-proof-v0.1",
  "status": "unavailable",
  "reason": "The defective revision requires a retired external service."
}
```

Use the generated Markdown as PR or handoff evidence. Keep durable architectural
rationale in an ADR or issue rather than expanding the Quality Runner artifact
into a history store.
